# 执行日志使用说明

YLCoder 默认把每次任务的模型请求、回复和工具过程写入本地 Markdown。日志独立于会话检查点，可用于查看实际提示词、分析重复输入、排查重试和工具失败。旧配置无需新增字段；退出旧进程后重新运行 `ylc`，从下一次提交任务开始记录。

## 先这样使用

在要处理的项目目录启动，提交一次任务，结束后输入 `/logs`：

```powershell
cd "D:\code\你的项目"
ylc
```

```text
/logs
```

界面列出**当前会话最近 10 个任务日志的绝对路径**，第 1 项最近更新。用编辑器打开某个 Markdown 文件，在预览中可以点击重复内容的引用，跳转到首次记录。更多文件可以直接在列出的目录中查看。

不进入交互界面也可以查看：

```powershell
ylc logs
ylc logs 你的完整会话ID
ylc --workspace "D:\code\另一个项目" logs
ylc --json logs
```

- `ylc logs`：列出当前工作区各会话最近 10 个日志文件。
- `ylc logs 会话ID`：只列出该会话最近 10 个文件。这里使用完整 ID；`/resume 1` 的快捷序号不是日志命令参数。
- `--workspace`：显式选择其他工作区。省略时使用执行命令的目录。
- `--json logs`：供脚本读取，返回 `directory` 和 `files`。

这些查看操作只读本地目录，不调用模型。独立的 `ylc logs` 不加载模型配置、凭据或 MCP，配置损坏时仍能定位已有日志；因此它返回的 `enabled` 是 `null`，表示没有读取当前记录开关。交互中的 `/logs` 可以显示已经加载的开关。

## 文件在哪里

每个提交的任务一个文件，存放在该任务工作区：

```text
.harness/
  logs/
    完整会话ID/
      UTC时间-随机ID.md
```

例如在 `D:\code\demo` 执行 `ylc`，日志就在 `D:\code\demo\.harness\logs`，与安装目录无关。文件名使用 UTC 时间，文内也明确标注 UTC。

`/resume` 或 `ylc resume` 后提交新任务，会在原会话目录新增文件。`/rewind` 保留当前会话 ID 和旧日志；回退后提交的任务仍新增文件，可追溯回退前的过程。会话历史保存在 `.harness/sessions`，日志本身不承担恢复和回滚。

普通非交互任务在完成时显示日志路径，`--quiet` 可抑制此提示。`ylc --json run "你的任务"` 的任务报告包含 `traceFile`；关闭记录或未能创建日志时为 `null`。文件存在不代表记录完整，应检查文件末尾的任务状态或停止记录提示。

## 会记录什么

| 记录 | 可查看的内容 |
| --- | --- |
| 模型请求 | 请求编号、主模型或审核模型、厂商 ID、模型名、流式标记、时间和迭代编号 |
| 请求消息 | 系统提示、用户内容、助手历史、工具调用和工具结果；按实际请求顺序保存 |
| 工具定义 | 工具名、描述和输入参数结构 |
| 模型回复 | 已解析的主模型正文、工具调用、结束原因、耗时，以及厂商报告的输入/输出/缓存 token |
| 模型失败与重试 | 失败请求编号、异常类型和脱敏后的错误摘要；每次重试单独编号 |
| 工具执行 | 工具名、调用 ID、参数、开始事件、完成或失败事件、结果摘要 |
| 审核模型 | 单独标为 `reviewer`，保存分类器请求及合法的结构化结论和简短理由 |
| 中断的流式回复 | 已产生文本的有限摘要与失败信息，不伪造完整回复 |
| 任务结束 | 完成/失败/取消等最终状态、时间和实际模型请求数 |

记录点位于**上下文整理之后、交给厂商适配器之前**。看到的是这次实际调用使用的 `ChatRequest` 逻辑消息和工具定义，能够观察压缩、裁剪后剩下了什么。完整会话历史可能比单次请求多，两者用途不同。

这不是原始 HTTP 抓包。适配器还会把逻辑请求转换为 Chat Completions、Responses 等协议字段；日志不保存授权头、完整配置、原始 SSE、厂商不透明元数据或私有推理。审核模型只保存通过结构验证的 `decision/reason`，格式无效的自由文本不会落盘。

用量为厂商返回值，不能用日志数字推算未报告的账单。数值为 0 也可能表示厂商没有报告。

## 重复提示词如何占位

同一个文件内，正文、工具参数和工具定义经过脱敏后计算摘要。已经出现的内容不再整段展开，显示字符数、摘要和“首次记录”的链接。例如：

```text
模型请求 #1：系统提示和工具定义完整展示。
模型请求 #2：未变化的系统提示和工具定义引用首次记录。
             新的工具结果或用户内容按限制展示。
模型请求 #3：相同内容继续引用，变化部分另行记录。
```

每个任务文件都能独立阅读，引用只指向本文件。新任务不会依赖上一个日志文件。

占位只减少本地日志重复，**不会修改发给模型的提示词，也不会额外调用模型**。它本身不减少模型输入 token；上下文预算和压缩仍由智能体原有机制负责。

## 展示长度和关闭方式

在私有配置文件中加入或修改以下段落，例如 `$HOME\.code-harness\config.yaml`：

```yaml
trace:
  enabled: true
  tool-result-max-chars: 2000
```

- `enabled` 默认 `true`。设为 `false` 并重新启动后，停止创建新日志，已有文件仍可查看。
- `tool-result-max-chars` 默认 2,000，可设 128–32,000。控制日志中的单条工具结果、错误和未完成回复摘要。
- 系统提示、用户/助手正文、工具定义和参数的单段保护上限为 1,048,576 个字符，超过时明确截断。
- 每个任务文件最多 32 MiB、65,536 条内容引用。达到保护上限会写停止记录标记并提示，任务继续执行，后续事件不再记录。

以上长度按 Java UTF-16 单元计算，不是 token 数。先脱敏再计算摘要和截断。日志展示限制不会缩短正常的工具结果或改写模型上下文；工具本身和智能体的既有结果上限仍可能先限制工具输出，日志无法补回上游已经丢弃的内容。

没有自动按天清理或跨文件去重。日志目录会创建自己的 `.gitignore`，普通 Git 操作默认忽略这些文件；已跟踪的日志不受忽略规则保护。需要清理时，先退出正在运行的任务，保留需要的文件再清理对应目录。

## 凭据和故障边界

已配置的主模型/审核模型密钥、额外请求头中的配置值以及常见凭据字段和密钥格式会遮盖。工具参数按结构脱敏；无效 JSON 不按原文落盘。任意项目文本中的未知秘密无法保证全部识别，因此日志应保留在本地，分享前自行检查。

日志包含项目代码、用户问题、工具命令和回复。程序尽可能为新文件设置当前用户私有权限，并检查日志目录、链接/junction、文件身份和异常外部追加。路径重定向、目录不可写或磁盘写入失败只提示一次并停止本轮记录，模型和工具任务继续；程序不会换到其他目录保存。

查看日志不会读取正文或发送给模型。默认项目列目录和搜索跳过 `.harness`；明确调用 `read_file` 读取允许范围内的日志文件仍遵循现有文件工具权限。此机制不禁止显式读取日志。

不能从旧会话检查点完整还原以前每次发送的请求，尤其是压缩投影、审核请求和重试。因此该功能只记录启用后的新任务。

日志写入会进行本地文件检查与落盘，未对其额外磁盘开销做单独性能基准。本功能没有新增模型调用或 token 开销。

## 本地验证

先打包，再运行：

```shell
python scripts/smoke_execution_trace.py
```

可针对 Windows 已安装的全局入口验证：

```powershell
python scripts/smoke_execution_trace.py --launcher "$env:LOCALAPPDATA\YLCoder-harness\bin\ylc.cmd" --output target/execution-trace-global-smoke.json
```

脚本使用隔离工作区、独立 home 和 localhost 模型，覆盖 Chat/Responses、工具摘要与引用、会话恢复/回退、本地查询、独立审核模型、三次 1/2/4 秒重试、部分回复失败、关闭记录和写入失败。不会加载真实用户模型配置或请求真实厂商。具体证据见 [执行日志验证记录](EXECUTION_LOGS_VERIFICATION.md)。
