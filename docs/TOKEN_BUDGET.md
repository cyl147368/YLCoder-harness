# 上下文预算、压缩与按需检索

默认模式把完整会话和每次发送给模型的请求分开处理。完整历史用于恢复、回退和查看；模型请求保留全部用户原文、系统规则、近期轮次，加上旧轮次的结构化摘要。大段工具原文先脱敏存档，模型按需分页读取。压缩改变请求内容，不删除已保存的对话记录，也不回滚磁盘操作。

## 输入预算如何计算

有效输入上限 = min(用户输入上限, 模型总容量 − 输出预留 − 推理预留 − 安全预留)。随后核心从该上限中扣除工具 schema 的本地估算，为消息留出实际预算。

- 用户输入上限：`agent.context-budget-tokens`，默认48,000。
- 输出预留：`agent.max-output-tokens`，默认3,000；显式空值仍预留3,000。
- 推理预留：`agent.reasoning-reserve-tokens`，默认0。使用会占用上下文的推理模型时按厂商说明配置。
- 安全预留：`agent.context-safety-margin-tokens`，默认2,048。

模型容量按以下顺序解析：`agent.model-context-windows` 中与模型名完全相同的项 → 通用 `agent.context-window-tokens` → 少量已知模型家族的保守内置值。未知模型使用用户输入预算加预留构成临时规划值，来源标为“自定义输入预算”，不能把它当作厂商的真实容量。新模型、网关别名和自定义厂商建议显式配置容量；使用 `/model` 切换模型时会重新解析预算和计数器。

例如模型总容量16,000，输出预留3,000，推理预留1,000，安全预留2,048，即使用户输入上限48,000，有效输入最多9,952；工具 schema 还会占用其中一部分。预留后不足64 tokens 会在网络请求前失败。

## 默认计数与显式选择

`agent.token-counter: auto` 是默认值。已知 GPT-4.1/4o/5/6 和 o1/o3/o4 名称选 `o200k`；较旧 GPT-4/3.5 名称选 `cl100k`；其他模型选 `conservative`。识别编码不会推断未知模型容量。用户可显式覆盖：

```shell
ylc run "修复失败的解析器" --token-counter o200k --context-budget 12000
```

支持 `auto`、`cl100k`、`o200k`、`conservative`、`utf16`；未知名称会在模型请求或MCP启动前失败。`utf16` 保留旧版兼容，但可能低估中文，不建议作为自定义模型的默认统计。

CLI使用随包Jtokkit 1.1.0对规范JSON进行普通分词。统计涵盖角色、消息正文、工具名称与参数、不透明厂商元数据、工具说明和schema，并加入显式的消息框架预留量。保守模式按ASCII字符和非ASCII UTF-8字节估算，再加余量。各记录独立编码后求和；以上均为本地预算统计，不是厂商账单计数，也不是绝对安全的传输容量证明。厂商模板、特殊token和分词器差异仍需用真实返回用量校准。

不可变消息和工具定义使用有界身份缓存；每类缓存最多256项、1,048,576个序列化UTF-16单元。它们不额外保存序列化源码JSON，不持久化到磁盘；过大的记录不缓存，淘汰不改变计数。重新创建运行时或切换模型会重建计数器。

## 结构化语义压缩

默认 `agent.context-semantic: true`。工作请求达到有效消息预算的85%时尝试整理旧轮次，目标压至65%；最近4个用户轮次保留原文。只有一个用户轮次的长任务在足够多完整块之后，可整理旧块并保留最后6个完整块。工具请求及其全部结果始终作为完整块处理，不拆成孤立结果。带不透明厂商回放证据的边界不会直接跨过并用摘要替代。

旧历史被整理为七类事实：目标、约束、决定、完成事项、待办、失败、文件/存档引用。摘要无工具权限，不批准任何操作，不把仓库内容升为系统指令。默认模式额外保留所有用户消息原文，因此旧的否定条件不只依赖模型摘要。若用户原文本身已经过大，系统会在本地失败，而不是悄悄删掉要求。

每次更新摘要都重新读取相应的原始历史，不递归“摘要旧摘要”。每个原文摘要请求最多使用16,000的规划输入预算，再受摘要模型容量约束；单次整理最多8个原文请求。各分块结果严格验证JSON格式，按字段合并、去重，最后验证总摘要预算。默认摘要上限1,500 tokens。

新摘要只有在缩小请求且达到目标比例时才接纳，保存原文边界和SHA-256指纹供后续复用。原文前缀变化或回退后指纹不符会使旧摘要失效。失败、格式无效、超预算或近期内容过大时降级为本地裁剪，完整会话仍保留；失败后至少新增16条消息才再次尝试语义摘要，避免每轮重复付费。

本地裁剪仍是最终预算保护：保留系统与必需用户文本、完整工具循环，不改调用参数、签名或不可裁剪的回放文本；可以移除较旧的可选块或缩短普通工具结果。默认语义模式保留全部用户原文；关闭 `context-semantic` 会使用兼容的旧式裁剪策略，旧的可选用户轮次也可能从请求中省略。过大的必需内容仍本地失败。

## 摘要连接和额外消耗

`agent.context-summarizer: {}` 默认沿用主厂商、地址、模型、密钥与协议。可仅配置 `model` 选同厂商另一模型，也支持 `provider/base-url/api-format/api-key/api-key-env/header-env`。更换厂商或地址不会隐式转发主连接的密钥和额外请求头；请独立配置。跨厂商省略地址时采用目标厂商默认地址。

摘要请求可能计费，使用独立无工具模型调用。报告总用量应包含已知摘要输入和输出；厂商不报告用量或请求失败不能认为免费。摘要会增加当前轮延迟和一次性token消耗，后续复用才能抵消；无需压缩时不发摘要请求。不要把单轮请求变小直接等同于总费用下降。

## 完整历史和工具原文按需找回

| 工具/数据 | 用途 | 边界 |
| --- | --- | --- |
| 会话检查点 | 保存完整活动历史，供 `/resume`、`/history` 和回退使用 | 单份32 MB；已有保存和锁保护仍生效 |
| `search_history` | 检索当前完整会话，找回旧要求、决定和工具引用 | 关键词1..256字符；每次最多8条有界片段，可用 `start_message` 继续 |
| `read_tool_output` | 分页读取大工具结果的脱敏原文，无需重跑工具 | 单份4 MB，总量64 MB，最多约512份；每页最多500行、8,000字符 |
| `repository_map` | 先定位相关源码路径和类型声明，再分段读正文 | 单次最多展示100文件；扫描最多10,000项或5秒，命中预算会标明不完整 |

大工具存档保存在工作区 `.harness/artifacts/`，以脱敏内容SHA-256命名并去重。模型收到首尾摘要、关键错误和 `archive_id`。无法安全存档、超出容量或磁盘不可用时明确提示当前只有摘要，不假装全文可找回。读取支持 `start_line/end_line`；超长单行可用返回的 `start_char` 继续。链接/junction、文件身份变化和内容摘要不符会被拒绝。

仓库地图是有界词法声明索引，覆盖Java等常见源码扩展；不提供完整AST、调用关系或语义向量检索。跳过 `.git/.harness/target/build/node_modules` 等目录，单文件最多256 KB，缓存按大小、修改时间和文件身份验证。历史检索也是关键词片段检索；不会自动提供跨项目长期记忆。

本地存档与会话仍可能包含项目内容。已知密钥和常见敏感字段会脱敏，但无法识别源码中所有秘密；分享前仍需检查。删除 `.harness/artifacts` 不会重跑工具，旧引用会变成不可读取；需要原文时应自行保留。

## 复现与验收

```shell
# 先构建，再用实际打包CLI和localhost厂商运行端到端检查
mvn verify
python scripts/smoke_context_optimization.py

# 输出中英文、四类计数器的五轮离线对照
java -cp harness-cli/target/harness-cli-0.1.0-SNAPSHOT-all.jar dev.codeharness.cli.ContextOptimizationBenchmark
```

基准固定模拟摘要，不测量模型语义能力或真实厂商账单。它同时报告原历史、旧式裁剪和新投影的请求输入总量，以及摘要的本地输入/输出成本和旧约束保留情况；判断是否节省需把摘要成本计入。计数器启动、I/O、HTTP和真实模型延迟与本地投影耗时不同，不能混用。

最终端到端测试结果、实际通过/跳过数量和剩余限制以本次测试报告为准；手册不把可运行命令当作已经通过的证据。

本轮实现的端到端验收、包含摘要成本的 token 对照及未验证边界见[上下文优化测试报告](CONTEXT_OPTIMIZATION_TEST_REPORT.md)。
