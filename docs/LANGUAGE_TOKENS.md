# 中文化与 token 用量对比

项目的 Markdown 说明、自然语言代码注释、系统与恢复提示词、工具说明、CLI 帮助及交互/错误文案已改为中文。命令、参数、标识符、协议字段、模型名称和历史实验数据保留技术原值。原始英文实验 JSON 与本次双语对照语料保留原文，便于核对和复算；它们不是需要阅读的使用说明。

第三方库、操作系统和外部工具返回的动态内容保持其原始语言；固定协议测试样本也保留技术原值。

本次固定语料里，中文在两种分词器下都比英文使用更多 token。中文化提高了可读性，不能据此宣称节省 token 或提速。

## 最接近一次模型输入的对比

分别启动中文化前后两个真实 CLI，在全新空工作区执行含义相同的任务，通过 localhost 模拟端点捕获首轮请求。每个版本恰好一次请求，均没有 Authorization，也没有调用真实模型。

英文任务：检查相关 Java 文件、集中修复并用适当测试验证。中文任务采用同样含义。两份请求都包含一个系统提示、一个用户任务和七个内置工具；除自然语言消息与说明外，完整请求中的机器结构严格相同。

以下统计捕获请求中排序、紧凑 JSON 序列化后的 `messages` 和 `tools`：

| 分词器 | 英文 token | 中文 token | 中文增加 | 增幅 |
|---|---:|---:|---:|---:|
| cl100k_base | 711 | 1,009 | 298 | 41.91% |
| o200k_base | 721 | 861 | 140 | 19.42% |

同一载荷的 UTF-8 大小为 3,682 → 3,735 字节，增加 53 字节（1.44%）。字节数和 token 数没有固定换算关系。

这里不包含厂商内部聊天模板、服务端隐藏内容或模型输出，也没有统计后续读取代码、工具结果和恢复历史。`model`、`stream`、`max_tokens` 等相同外围字段未纳入这张 token 表。它是一次首次请求的本地消息/工具计数，不是完整线上请求的计费量或一个真实编程任务的总消耗。

## 文档、注释和提示词语料

以下为中文化前后的固定文本，逐项分词后汇总。差值均为“中文减英文”，百分比按该类总量计算。

| 文本范围 | 配对数 | cl100k 英文 → 中文 | 增幅 | o200k 英文 → 中文 | 增幅 |
|---|---:|---:|---:|---:|---:|
| Markdown 全文 | 70 | 60,845 → 93,778 | 54.13% | 61,005 → 72,553 | 18.93% |
| 有对应关系的变化注释 | 199 | 3,281 → 5,907 | 80.04% | 3,290 → 4,495 | 36.63% |
| 系统/恢复/工具等运行提示文案 | 24 | 411 → 730 | 77.62% | 402 → 536 | 33.33% |
| 离线评测/基准提示文案 | 47 | 1,015 → 1,677 | 65.22% | 1,007 → 1,282 | 27.31% |

共 341 对文本，包含上表及一对真实 CLI 载荷，独立复算了 682 个字符串。文档、注释、提示词及载荷存在内容重叠，不能把各类别相加推断一次调用费用。文档和源码注释不会自动逐轮发送；只有读取并放入上下文的部分才会占用模型输入。

70 篇文档采用完整前后文本，保留历史事实、数字、命令和链接；其中开发语言约定按用户要求改为中文，少量过时状态增加了历史限定。因此这是项目实际中文化前后对照，并非每句话都只替换语言的受控语言学实验。两份已替换为当前分工的任务文件、本报告及后续新增进度不纳入文档语料。

注释仅纳入注释数量一致文件中变化的逐项文本。`scripts/check_latency_measurement.py` 和 `scripts/measure_latency.py` 因注释数量变化而排除；排除记录保存在语料中。Java 使用词法正则提取，Python 包含注释和文档字符串，YAML 只包含独立注释行；不宣称覆盖任意语法的全部注释。正式提示词语料按独立文案组织，不能用其总数替代包含重复说明、动态值及完整 schema 的实际请求计数。

## 如何复算

在源码项目中先构建，再运行：

```shell
mvn -B verify
python scripts/compare_language_tokens.py
```

便携包内包含同一脚本、固定语料及结果；安装 Python 3 和 Java 21 后，在解压目录执行以下命令即可复算，无需 Maven：

```shell
python scripts/compare_language_tokens.py --output language-tokens-recount.json
```

脚本通过打包 jar 中的 Jtokkit 对文本分别执行 `cl100k_base`、`o200k_base` 的普通文本分词，同时计算 UTF-8 字节数；不访问模型或网络。默认读取 [固定双语语料](benchmarks/language-corpus-v1.json)，默认写入 [逐项计数与汇总](benchmarks/language-tokens-v1.json)。语料、计数脚本及 jar 的 SHA-256 记录在结果中；计数期间输入发生变化会失败。重新构建 jar 后，其文件哈希可能变化，文本计数应保持一致。当前入口上限为 1,000 个字符串和 8 MB 输入；超过范围会失败。

英文捕获产物 SHA-256：`43d272eec8e2087f3e72bb5147cfdec5e2fba00be7614d7fef4dfe0b23d1e3a6`。

中文捕获产物 SHA-256：`237dad5dd6cd78598060e3ceafa0900bf4a2d6b21f8980d10535c87216f14732`。

固定语料 SHA-256：`707ae70279645b64cc2ef626670cad0aa57740950828dc0554750d9a190cc9ad`。

## 对费用和使用方式的含义

CodeGo 代理后的不同模型不一定使用这两个分词器。真实费用还取决于模型、输出长度、缓存命中、工具历史和厂商价格。本次没有通过真实模型比较中文与英文的修复质量、输出用量或延迟，因此无法给出等质量任务的账单涨幅。

当前默认 `utf16` 计数仍是兼容性的近似值，尤其可能低估中文。需要按本地分词器严格控制上下文时，可显式使用 `--token-counter o200k` 或 `--token-counter cl100k`，并依据实际模型选择；它们也不能保证与厂商计费完全一致。详见 [token 预算说明](TOKEN_BUDGET.md)。
