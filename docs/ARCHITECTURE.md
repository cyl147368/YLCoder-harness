# 架构与实现状态

## 模块边界

`harness-core` 不依赖厂商 SDK 或 JSON 库。它定义消息、工具调用、厂商元数据、schema、用量、模型契约、工具注册表、上下文压缩器和有界智能体循环。

`harness-providers` 为 Chat Completions、Responses、Anthropic Messages、Gemini generateContent 和 Azure 实现原生 HTTP 适配器，并提供真正的 LangChain4j OpenAI 适配器。ModelProvider/ServiceLoader 支持扩展其他厂商。密钥由 CLI 读取并在内存中传递；适配器禁止重定向，并对错误信息脱敏。

自定义厂商实现公开的 `ModelProvider`/`ProviderConfig`/`ChatModel` SPI，通过应用 classpath 中的 `META-INF/services` 加载。支持的扩展启动方式为 `java -cp "custom.jar:lib/ylc.jar" dev.codeharness.cli.HarnessCli`（便携包示例，Windows 的 classpath 分隔符改为 `;`）；`java -jar` 不会发现其归档以外的 jar。扩展与公开记录类型的版本绑定；记录类型变化后必须重新编译。本地外部厂商冒烟测试会编译扩展，并通过实际 CLI 调用，包括跨进程元数据恢复；这不能证明真实厂商的协议行为。

`harness-cli` 负责 picocli 命令、严格 YAML 加载、工作区工具、MCP stdio 生命周期、独立的 shell/外部工具审批、对话记录存储、进度输出和离线基准。私有配置支持直接填写 `api-key`，也支持 `api-key-env` 引用环境变量。显式 CLI `--api-key-env` 优先；否则非空白 `api-key` 优先于配置变量/厂商回退变量。密钥仅在内存中传给适配器，不持久化到会话或日志，配置解析异常也不回显配置值。会话内容本身可能包含私有源码或用户主动粘贴的内容，必须妥善保护。

## 任务执行

1. 以进程调用目录选择工作区；仅显式 CLI `--workspace` / `-w` 可以覆盖。随后加载配置并选择模型/厂商。旧 YAML `workspace` 字段保留解析兼容，但 CLI 忽略其值，防止配置把工具和会话切到其他目录。
2. 注册稳定有序的工具集，从输入预算中预留估算的 schema 大小。
3. 检查取消状态并压缩消息记录，保留系统指令和原始/最近的用户意图。
4. 请求模型输出。拒绝截断、被过滤、未知或格式错误的完成状态，不能把它们当作成功。
5. 执行副作用前先持久化助手的工具请求。按修改屏障执行工具，按调用顺序持久化每个结果，并在模型调用上限内继续。
6. 保存最终状态，报告状态、文本、用量和耗时。

工具默认串行执行。将 `maxParallelReads`/`--parallel-reads` 设为 2..8 后，连续且明确安全的读取会在虚拟工作线程上分批有界执行。只有内置 list/search/read 工具选择加入；修改、命令、变更报告、未知工具和 MCP 调用仍是串行屏障。即使读取乱序完成，协调线程的检查点/结果也保留调用顺序。取消或检查点失败会中断待处理读取，并阻止后续工具。扩展必须只读、线程安全并配合中断；不配合的扩展可能在取消后继续运行，系统不会强制杀死工作线程。原有六参数 options 构造器仍保持串行行为；使用记录规范签名的外部代码需要重新编译。

原生 Chat Completions 和 LangChain4j 适配器流式输出文本，并在执行前组装完整工具请求。原生传输限制 SSE/响应体累积量和完整的请求头/响应体截止时间，要求 finish 与 DONE 同时存在；网关忽略 stream 并返回 JSON 时可接受，但不会合成增量，也不会自动重试。`--no-stream` 选择普通请求。Responses、Anthropic 和 Gemini 仍为同步方式。Responses 使用无状态文本/函数请求，并回放工具轮次和最终轮次的加密推理。Gemini 保留受支持的 thought/text/function 部分的顺序。两者都使用不可变消息元数据，检查点/恢复也会保留；发送 HTTP 前会验证元数据对应的可见文本/工具投影。未启用自动模型重试。详见[原生流式契约](NATIVE_STREAMING.md)。

## 上下文设计

schema 会递归复制并排序；工具顺序与注册顺序一致。工具输出在产生时和插入循环时均受限。压缩器把助手工具请求及其所有结果视为不可拆分的块。它移除较旧的可选块，并留下数字化的助手元数据摘要，绝不把仓库/工具文本提升为系统指令。它可以裁剪保留的工具输出，但不会改变调用 JSON、不透明厂商元数据或带有回放证据的消息文本。不可缺少的内容无法放入预算时在本地失败。完整的可选历史块仍可能被丢弃；不承诺无限保留全部厂商历史。

默认估算为每 token 四个 UTF-16 代码单元，并显式计算元数据/schema 开销。CLI 可选的 `cl100k`/`o200k` 策略通过核心 `InputTokenCounter` 契约，对规范消息/schema JSON 计数，并添加消息框架预留量。压缩会重新测量候选裁剪内容，并在有界内存中缓存不可变消息的计数。CJK、代码、转义和厂商模板可能带来显著差异；预算约束的是本地统计，不是厂商账单或精确传输格式。输出上限单独控制。详见 [token 预算统计](TOKEN_BUDGET.md)。数字摘要记录省略量，不记录被删除文本中的语义决策。更丰富的状态保留和编程质量实测仍有后续工作。

## 恢复

SessionStore 在规范工作区中保存带版本的 JSON 对话检查点。协作文件锁防止同时写入；有界、严格的 JSON 解析会拒绝身份损坏或格式错误的记录。临时文件使用原子替换，中断时被忽略。支持 POSIX 时应用私有权限。不承诺基于 fsync 的断电持久性。

恢复时，未答复的工具调用会收到“效果未知”结果。模型重试前必须检查当前文件；循环绝不会自动重放不确定的写入/命令。原始厂商/模型会保存，但端点/凭据配置必须重新提供。工作区身份检查避免意外加载到另一个仓库。

## 文件与命令边界

WorkspaceTools 解析规范路径，拒绝路径穿越和符号链接/junction 逃逸，限制文件大小/输出，并原子替换普通 UTF-8 文件。字面量编辑要求恰好一个匹配，可附加哈希前置条件。规范路径检查无法消除所有恶意并发文件系统竞态。

文件读取对实际消耗的数据执行 1,000,000 字节上限，包括初次大小检查之后增长的数据。读取/搜索使用严格 UTF-8 解码；搜索跳过无效或过大的文件。读取范围必须是真正的 32 位 JSON 整数。分块和行边界会检查中断；阻塞的文件系统操作仍取决于平台行为。

shell 默认采用本地候选门禁和独立审核子 agent 两层判断。只有有限的只读命令能进入模型审核；删除、安装、网络、解释器、构建/测试脚本及复杂 shell 直接转人工。审核上下文与主智能体隔离，不注册工具，只发送原始命令、规范工作区和实际执行参数；使用当前选定的厂商和模型，要求明确的审核结论。通过后执行对应参数，不能把审核放行扩大为其他命令或工作区的授权。

`ReadOnlyCommandGate` 只接受手册中列出的精确目录查询和 `git branch --show-current`。目录查询使用系统绝对路径与固定参数；Windows 通过 `GetSystemDirectoryW` 定位 cmd，不启动用户提交的 shell 文本。Git 只从调用者原有 PATH 的工作区外绝对目录选择原生程序，显式锁定 `--git-dir`、`--work-tree`，拒绝父仓库发现、`.git` 指针、共享对象库和内部链接；元数据检查上限为 32 层、10,000 项。受限执行移除 `GIT_*`、`DIRCMD`、`RIPGREP_CONFIG_PATH`、Java 自动加载选项，并关闭 Git 全局/系统配置、pager、fsmonitor 和可选索引写入。`status`/`diff` 可能执行 clean/process filter，即使指定 `--stat`、`--no-ext-diff`、`--no-textconv` 也不能保证不执行项目脚本，因此始终转人工。已有文件系统、程序及目录身份会在审核后和缓存命中时复核；Windows 额外使用卷号和 128 位文件 ID，避免 NIO `fileKey` 为 null 时误用已替换目录的批准。这些检查仍不是操作系统沙箱。

审核响应必须是唯一 `decision` 字段的 JSON 对象，值为 `approve` 或 `manual`，且正常 STOP、没有工具调用；多余字段、重复键、尾随文本、代码块和截断响应都不能授权。审核请求不写入主会话，失败原因只显示本地固定文案。已失败或转人工的相同执行计划在该任务内也不重复请求模型。主结果 `agentUsage` 与 `review.usage` 分别记录，`usage` 为两者已知用量合计。

默认 `permissions.auto-review: true`。`--no-auto-review` 或可信配置关闭后逐项手动审批；显式 `--allow-commands` / `permissions.allow-commands: true` 预先放行所有命令，优先于自动审核开关。审核单次输出最多 96 tokens，默认超时 10 秒、每任务最多 8 次，分别可配置为 1～30 秒、1～32 次；不占主智能体迭代上限。仅通过的完全相同工作区、命令和执行计划可在单任务内复用；手动批准不缓存，下一任务和新进程恢复重新审核。失败、超时、格式不明确或次数用尽均转人工，非交互输入直接拒绝。MCP 的独立审批不使用 shell 审核结果。

审核也是可能计费的模型调用；`review` 单列其请求和已报告用量，顶层 `usage` 包含主智能体与审核已报告用量。超时或用量缺失不表示免费。进度使用 stderr，`--quiet` 隐藏普通进度，但需人工处理的原因和提示仍显示。命令在工作区中启动，但拥有宿主用户权限；自动审核不是操作系统级沙箱，不宣称其文件系统/网络访问被限制在工作区。输出并发排空以避免管道死锁；超时会触发尽力而为的进程树终止。

CLI 任务和手动权限输入由一个 TerminalInput 管理。Windows 控制台使用 `ReadConsoleW`，其他控制台使用 `Console.readLine`，避免多个缓冲消费者争抢 stdin。管道模式通过一个缓冲严格 UTF-8 读取器读取任务行；不能自动批准的 shell 请求和未预先授权的 MCP 请求直接拒绝，不消耗任务输入。权限提示使用 stderr；手动审批只有明确回答 y/yes 才授权操作。注入输入测试验证顺序和拒绝行为，不能替代实体键盘与所有输入法的验收。

命令超时/中断清理把子孙进程发现、直接终止和每个管道关闭隔离到守护工作线程。卡住的原生清理操作不能无限阻塞调用者。正常输出排空在进程等待结束后最多等待两秒。子孙进程终止是尽力而为，可能遗漏脱离或重新归属的子进程；这不是操作系统作业/进程树隔离保证。不响应的原生清理线程可能在工具调用结束后仍存活。

成功的 write/edit 工具返回有界的上下文差异。`changes` 仅将已追踪路径与有界的内存原始快照比较，撤销后仍保留基线。新的 CLI 调用会重新开始追踪。唯一行锚点差异算法避免二次方 LCS 分配；输出可能不是最小差异，也可能是截断的审阅展示。详见[变更报告说明](CHANGE_REPORT.md)。

可信配置通过可关闭的客户端生命周期注册 MCP stdio 工具。按换行分隔的 JSON-RPC 帧、工具发现、schema 和输出都有显式限制。调用使用独立权限；超时/中断会停止进程。支持静态工具发现；HTTP 传输和其他 MCP 能力仍未实现。详见 [MCP 说明](MCP.md)。

## 验证与调研

测试使用确定性的本地 HTTP 服务、模拟模型轮次和临时工作区。打包冒烟脚本运行真实 jar 和 Java 编译器，不使用真实凭据。平台限制以跳过项报告。

设计参考链接见 [RESEARCH.md](RESEARCH.md)。harness 借鉴显式工具循环、有界上下文和持久检查点思路，没有嵌入外部智能体运行时。尚待实现的能力必须在工作计划中明确列出，不能描述为已实现。
