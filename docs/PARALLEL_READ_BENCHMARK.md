# 有界并行读取基准

Windows 11 / Java 21.0.10 本地测量：串行 p50/p95 为 741.024/744.4713 ms，四路读取 p50/p95 为 184.2746/185.5673 ms。十个测量样本全部通过输出/屏障检查；观测读取峰值为一与四。每个样本使用两个脚本化模型请求，序列化请求字节均为 3,255。原始证据：[parallel-reads-v1.json](benchmarks/parallel-reads-v1.json)。只有在此带延迟的模拟工作负载中，经过时间约降低为原来的 1/4.02；未测量真实磁盘/厂商/编程速度或 token 节省。

`dev.codeharness.cli.bench.ToolExecutionBenchmark` 使用真实 `CodeAgent`、两个脚本化模型响应和两个本地夹具工具。先执行四次各等待 80 ms 的读取，再由不安全修改递增状态，然后执行另外四次各等待 80 ms 的读取。比较读取并发上限一和四；每种模式预热一次，再各测量五个新状态样本。每个样本交替执行顺序。不使用网络、凭据、真实磁盘工作负载或模型服务。

JSON 报告记录最近秩 p50/p95 的 `CodeAgent.run` 经过毫秒数、各样本观测到的最大活动读取和重叠、最终状态、完成读取数、模型请求数、逐请求消息/schema 数和序列化请求字节。计时包含模拟等待，不包含 `CodeAgent.run` 之外的初始化、JSON 报告生成和进程启动。小样本 p95 即最大观测值，不是生产尾延迟估算。

正确性检查独立于计时：结果 ID/名称/内容严格有序；修改前全部读取观察到零，修改后全部读取观察到一；读取不与修改重叠；恰好八次读取完成、两个请求发生、最终状态为一。两种模式必须具有相同请求数和序列化载荷大小。违反并发上限会使基准失败。报告实际重叠，而非从经过时间推断；没有重叠时不会编造提速结论。

成功构建 reactor 后运行：

```shell
java -cp harness-cli/target/harness-cli-0.1.0-SNAPSHOT-all.jar dev.codeharness.cli.bench.ToolExecutionBenchmark
```

它模拟独立读取等待延迟的工作负载。任何观测速度差只适用于所测宿主上的该夹具，不能证明真实编程、磁盘读取、厂商生成更快或 token 成本更低。针对性测试使用更短延迟检查正确性和报告结构，不设速度阈值。负责人负责串行 Maven 验证和实际基准归档；这份交接本身不宣称测试已通过。
