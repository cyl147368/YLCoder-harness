## 2. 具体测了什么，对你有什么用

这里的“端到端”，就是从启动打包后的程序开始，实际走完请求模型、执行工具、保存会话、退出和恢复等流程，而不只单独检查某一个函数。测试使用独立的临时工作区和配置，不使用你的日常会话和厂商密钥。

### 两种接口、四种情况都跑了一遍

Chat 和 Responses 是两种模型 API 请求格式。我们分别测试了摘要返回正常、摘要返回错误格式的情况：

| 模型接口 | 模拟情况 | 测试结果 |
|---|---|---|
| Chat | 摘要格式正确 | 任务完成；重启恢复后能复用摘要 |
| Chat | 摘要格式错误 | 没有保存坏摘要；改用本地裁剪后继续完成任务 |
| Responses | 摘要格式正确 | 任务完成；重启恢复后能复用摘要 |
| Responses | 摘要格式错误 | 没有保存坏摘要；改用本地裁剪后继续完成任务 |

“本地裁剪”是指不再依赖这次失败的摘要，把较旧的助手回复和工具内容缩短，同时保留必须保留的内容。

### 按实际使用场景检查

| 你可能遇到的情况 | 测试怎么做 | 结果及含义 |
|---|---|---|
| 聊得久了，担心早先的要求被丢掉 | 放入 12 轮历史，在中间写下“禁止删除数据库并保留审计记录”，再触发整理 | 后续发给模型的请求仍包含这句原文；保存的会话历史也完整。这里只证明文字保留，不代表模型必然遵守 |
| 关闭程序后，恢复会话还要重新整理一遍 | 在摘要正常的两组中，启动新进程恢复会话，并更换主模型 | 有效摘要被复用，没有再次请求摘要模型 |
| 摘要出错，任务跟着卡住或反复调用 | 让摘要模型返回不符合要求的数据 | 每组只尝试了 1 次摘要，随后使用本地裁剪并完成任务 |
| 需要找回前面说过的话、看过的代码位置 | 让主模型依次调用历史搜索和仓库索引工具，再回答 | 工具调用和返回内容符合预期；当前会话历史可以按关键词查找 |

此外，原有的请求日志、Responses 接口、token 预算和意图识别测试也通过了。例如：闲聊不提供工具，分析和计划提供读取类工具，执行任务才提供写入工具。模拟请求失败时，重试间隔也实测接近设定的 1、2、4 秒。

## 3. token 到底省了多少

Token 可以理解为模型处理文字时使用的计量单位，不能简单按“一个汉字等于一个 token”换算。不同模型的分词方式不同，所以本次用了四种计数方式分别对照。

测试准备了 12 轮旧对话，再连续发起 5 次请求。每一行里，新旧方案使用相同的历史、预算和计数方式。

**新方案总量已经包含“生成摘要”的消耗，不能只看主请求变短了多少。** 两边都没有计入主模型最终回答的输出，也没有换算价格或缓存折扣，所以这是特定范围的 token 对照，不是完整账单。

| 样本文本 | 计数方式 | 旧方案总量 | 新方案总量（含摘要） | 变化 |
|---|---|---:|---:|---|
| 中文 | utf16（旧版估算） | 13,474 | 11,410 | 减少 15.32% |
| 中文 | cl100k | 40,515 | 35,948 | 减少 11.27% |
| 中文 | o200k | 36,655 | 32,444 | 减少 11.49% |
| 中文 | conservative（保守估算） | 177,250 | 180,025 | **增加 1.57%** |
| 英文 | utf16（旧版估算） | 47,331 | 39,036 | 减少 17.53% |
| 英文 | cl100k | 32,915 | 29,694 | 减少 9.79% |
| 英文 | o200k | 32,915 | 29,495 | 减少 10.39% |
| 英文 | conservative（保守估算） | 72,405 | 65,419 | 减少 9.65% |

这组数据有三个容易误解的地方：

1. **第一次整理可能更贵。** 例如中文 o200k 场景，第一次主请求加摘要消耗是 28,754，而旧方案第一次是 7,177。摘要反复复用后，才在本例的 5 次请求累计对比中省下 11.49%。所以不能承诺每次请求都省。
2. **多用 1.57% 的那组确实没有省。** 按保守方式计算时，原文超过了单次整理最多 8 个分块的限制，程序没有请求摘要模型，转而使用本地裁剪。新方案保留了旧方案省略的用户要求，因此多用了 2,775 tokens。
3. **这不能用来判断“中文比英文贵多少”。** 中英文样本和预算不同，并非同一段内容的严格翻译对照；utf16 也只是旧版估算。摘要回复是固定的模拟数据，真实模型生成的摘要长度和质量还需要另测。

8 组样本里，新方案最终请求都保留了用来检查的那条中间要求，旧方案都没有保留。它说明这次优化同时关注要求保留和请求大小，但并不证明摘要的其他内容都准确。

本次也记录了运行时间，不过包含程序启动、文件操作和退出，没有同条件的旧版本速度对照，**所以暂时没有“提速多少”的结论**。

## 5. 还有哪些限制

| 需要知道的限制 | 对实际使用的影响 |
|---|---|
| 摘要仍然可能遗漏细节 | 默认保留全部用户原文和系统规则，较旧的助手回复、工具结果会被精简。细节需要从保存的历史或存档中找回；保留下来的必需内容如果仍然超出预算，程序会停止请求 |
| 本地保存和发给模型的内容是两回事 | 正常保存成功时，压缩不会删除会话文件中的原始历史。但模型每次看到的是整理后的版本，而且会话与工具存档都有容量上限，不能无限保存或无限发送 |
| 生成摘要本身也要请求模型 | 首次整理可能增加等待和消耗。成功摘要能在重启后复用；摘要失败后的“暂停尝试一段时间”目前只在当前进程有效 |
| 历史与代码检索还比较基础 | 历史搜索只查当前会话的关键词；仓库索引主要找代码声明位置，还不能完整分析函数调用关系，也没有跨项目长期记忆 |
| 测试没有覆盖所有真实使用环境 | 真实厂商的摘要质量、费用、速度和缓存收益均未测；Linux/macOS、真实 IDEA 终端及 16 项被跳过的测试也未验收 |

如果下一步要确认真实收益，应让新旧版本完成同一批实际任务，对比总费用、等待时间、要求有没有遗漏，以及最终代码能否通过验收。本报告目前能支持的结论，是上述本地流程与数据检查已通过。

<details>
<summary>展开：上下文处理规则和容量上限</summary>

- 默认开启语义摘要；上下文达到预算的 85% 时触发，目标降到 65%；保留最近 4 个用户轮次，摘要上限 1,500 tokens。保留全部用户原文优先于达到目标比例。
- 默认 `auto` 计数会选择已知编码或保守估算。可用输入预算会扣除回答输出、推理、安全余量和工具定义；本地估算不等于厂商账单。未知模型、切换模型、中文必需内容超预算等情况有测试。
- 更新摘要时重新读取对应的原始历史，不反复压缩旧摘要。摘要必须符合七类事实数组的 JSON 格式；重复字段、多余尾随内容、工具调用、异常结束状态及超预算结果都会被拒绝。格式正确仍不代表语义没有遗漏。
- 摘要请求使用脱敏后的原文，不给摘要模型执行工具的能力。可通过 `agent.context-summarizer` 指定独立模型；切换厂商或地址时，不会自动把主连接凭据转发过去。
- 保存的摘要快照包含原文范围及指纹，用来核对能否复用。工具调用与结果成组保留，厂商要求原样携带的回放数据不能随意裁剪。回退会清除旧快照。
- 单次整理最多分成 8 个原文请求，同步执行，每个请求最多等待 30 秒。摘要失败后，同一进程至少新增 16 条消息才再次尝试；失败冷却不跨进程保存。
- 会话文件上限 32MB。工具结果脱敏后按内容校验值归档，预览缩短后仍可引用同一存档；每项上限 4MB、总量 64MB、最多 512 项。`read_tool_output` 每页最多 500 行或 8,000 字符，超长行可用 `start_char` 继续读取。未捕获或超限截去的数据无法恢复。
- `search_history` 搜索当前完整会话，包括历史工具参数；`repository_map` 提供词法声明索引和有上限的缓存，文件列表与搜索支持分页。它不等于 AST（语法树）、调用图或向量检索。
- 日志记录压缩前后大小、预算、复用、降级、耗时，以及厂商已报告的摘要用量；缺失的厂商用量不算作实测值。
