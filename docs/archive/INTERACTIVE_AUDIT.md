# 交互工作流审计

负责人处理结果：`scripts/smoke_interactive.py` 现验证两个带工具的真实 JAR任务、两次提交输入之间观察到 COMPLETED检查点、独立进程恢复已完成会话、精确持久化用户/工具顺序、help/空白输入无调用、EOF状态，以及HTTP回合失败后成功。九次localhost请求通过。具体help/持久化缺陷已修复：任务前help说明 `/exit` 不创建可恢复检查点，任务后help给出有效恢复命令。此处仍未验证交互进程强制死亡、实体终端审批及OS信号；已有核心/会话子进程死亡测试只覆盖共享检查点机制。

只读审计 `HarnessCli.interactive`、`execute`、`prepare`、`Resume` 和现有测试。未改源码/测试、运行Maven或真实调用。负责人计划的管道双任务和独立进程恢复冒烟已覆盖主要正常路径；以下建议关注不同边界。

## 发现

1. **P3具体缺陷：help在会话存在前宣称可恢复。** 交互模式分配并打印ID、获取锁，`/help` 说明“/exit保存并退出，可使用 harness resume <id> 恢复”。但仅 `execute` 保存会话。输入 `/help\n/exit\n`，或 `/help\n` 后EOF，从未调用 `execute`；`newId`仅创建UUID，`lock`创建锁文件，没有会话JSON。因此宣称的恢复命令无法加载该ID。应限定help说明提交任务后才能恢复，或以定义状态保存初始仅系统消息会话。验收：help/空白行/exit零模型请求，文档恢复行为符合持久化。

2. **边界验收：任务失败后另一个任务。** 交互在FAILED/MAX_ITERATIONS后保留 `result.transcript()` 并继续，而run/resume结束各自进程。输入第一任务，使其在MAX_ITERATIONS结束并留下未回答修改调用，再输入第二任务。断言第二请求含合成中断结果，从不执行旧修改，保留两个用户消息顺序并进入新任务。断言退出码取最后任务；另测失败后立即EOF保留非零码。这是源码预期行为，不是已证明失败。

3. **边界验收：共享终端输入与审批。** 任务输入使用自己的 `BufferedReader(System.in)`，命令/MCP审批使用 `System.console().readLine`。管道测试无console，除明确授权外自动拒绝审批，因此不能证明终端审批输入归属或多行粘贴行为。同终端独立缓冲可能将审批行预读到任务读取器。真实终端/PTY验收应提交请求命令任务、回答审批、提交下个任务，检查每行仅到预期消费者。这是待验证平台风险，不是复现缺陷。有console时单一console读取器可避免竞争读取。

活跃任务期间关闭stdin不会中断任务：仅 `execute` 返回后再次 `readLine`。崩溃恢复冒烟必须在已知检查点实际终止进程；仅关闭stdin不测试中断。

## 已覆盖行为

命令路径在整个交互生命周期持有工作区会话锁，通过 `onCheckpoint` 在工具执行前保存助手检查点，保存每个工具结果检查点，每个任务后写最终结果状态。`/help` 打印带生成会话ID的恢复命令。`McpCliTest`证明 `/exit` 关闭配置的MCP子进程且无模型请求。`Run`、`Resume` 是独立命令，但其进程边界不能证明交互stdin顺序。

## 范围

共享读取器修复：负责人用单一TerminalInput负责任务及shell/MCP审批，替换竞争console/stdin消费者。五项独立注入输入CLI测试通过，覆盖顺序、管道拒绝、拒绝回答、EOF和读取失败；实际管道交互及MCP权限冒烟通过。这些测试不证明真实PTY/粘贴或信号行为。
